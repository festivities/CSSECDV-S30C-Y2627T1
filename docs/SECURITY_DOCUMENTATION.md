## 1. System Overview

SecureShop is written in Python 3 using only the standard library (`http.server`, `sqlite3`, `hashlib`, `hmac`, `secrets`). The whole application lives in `app.py`; data is stored in a SQLite database (`data/shop.db`).

The application has three roles, matching the checklist's pre-demo accounts:

| Role | Checklist name | Summary |
|---|---|---|
| `admin` | Website Administrator | Creates, deletes and assigns Administrator and Product Manager accounts; the only role that can read the audit log. |
| `manager` | Product Manager | Manages the product catalog and the status of every customer's orders. |
| `customer` | Customer | Self-registers; views products; places, edits and cancels only their own orders. |

Pre-demo accounts (created automatically on first run):

| Checklist item | Username | Password |
|---|---|---|
| 1.1.1 Website Administrator | `admin` | `Admin#Secure2026!` |
| 1.1.2 Product Manager | `manager` | `Manager#Secure2026!` |
| 1.1.3 Customer | `customer` | `Customer#Secure2026!` |

All three seeded accounts use the security question "What was the name of your first-grade teacher?" with the answer `Mrs. Evangelista-Santos`.

## 2. Security Modifications

### 2.1 Authentication

| Security Requirement / Issue | Vulnerability | Impact | Security Control |
|---|---|---|---|
| 2.1.1 Require authentication for all pages and resources, except those specifically intended to be public | Missing authentication on pages or resources (forced browsing). | An anonymous visitor types a URL such as `/admin/logs` or `/manage/orders` and reads or changes data without ever logging in. | Every request passes through one function, `dispatch()`. Each entry in the `ROUTES` table carries the set of roles allowed to use it. Only `/login`, `/register`, `/forgot`, `/forgot/reset` and `/static/style.css` are marked `public`. For anything else, `dispatch()` looks up the `sid` cookie (SHA-256 of the token is matched against the `sessions` table, with a 30-minute idle timeout). If there is no valid session the request is redirected (302) to `/login` and an `ACCESS FAILURE` entry is logged. Routes that are not in the table return 404, so there is no unlisted resource to reach. |
| 2.1.2 All authentication controls should fail securely | Errors in authentication code that leave the user logged in or let the request through. | A database error or malformed cookie during the session check results in the request being processed as if it were authenticated. | The default state is "denied". A session is only attached to the request after every check succeeds; any exception while loading the session or authorizing is caught and the request is denied with the 403 page. A handler exception returns the generic 500 page and never creates a session. Login creates the session as the last step, only after the password has been verified with `hmac.compare_digest`; locked accounts are refused even with the correct password. |
| 2.1.3 Only cryptographically strong one-way salted hashes of passwords are stored | Plaintext, reversible or fast unsalted password storage. | An attacker who obtains the database file reads every password, or cracks them with rainbow tables, and reuses them here and on other sites. | `hash_secret()` uses `hashlib.scrypt` (memory-hard KDF) with N=2^14, r=8, p=1, a 32-byte output, and a fresh 16-byte salt from `secrets.token_bytes(16)` for every password. The value is stored as `scrypt$<salt hex>$<hash hex>`. Verification recomputes the hash with the stored salt and compares in constant time with `hmac.compare_digest`. Security-question answers and all password-history entries are hashed the same way. Session tokens are stored only as SHA-256 digests. Plaintext passwords are never stored or logged. |
| 2.1.4 Authentication failure responses should not indicate which part of the authentication data was incorrect | Distinct error messages for "unknown user" and "wrong password" (user enumeration). | An attacker builds a list of valid usernames from the error messages, then concentrates password guessing on those accounts. | Every login failure — unknown username, wrong password, locked account, or badly formatted input — returns exactly the same response: "Invalid username and/or password." For unknown usernames a scrypt verification is still run against a dummy hash so response time does not reveal whether the account exists. The real reason is written only to the audit log. Password reset likewise answers "Password reset failed." for every failure, and shows a deterministic decoy security question for unknown usernames. Registration with a taken username answers "Registration failed. Choose a different username." |
| 2.1.5 Enforce password complexity requirements established by policy or regulation | Weak, easily guessed passwords. | Dictionary or credential-stuffing attacks succeed against accounts with passwords such as `password123`. | `v_password()` is the single password-policy function, used by registration, password change, password reset and admin account creation. It rejects any password that does not contain at least one uppercase letter, one lowercase letter, one digit and one non-alphanumeric character. A failing password is rejected (HTTP 400) and the failure is logged; it is never modified to fit. |
| 2.1.6 Enforce password length requirements established by policy or regulation | Short passwords that can be brute-forced. | An 8-character password hash is exhaustively searched offline after a database leak. | `v_password()` requires a minimum of 12 and a maximum of 128 characters. The upper bound prevents very long inputs from being used to exhaust CPU in the scrypt computation. |
| 2.1.7 Password entry should be obscured on the user's screen | Passwords shown in clear text while typing (shoulder surfing). | A person or camera behind the user reads the password off the screen. | Every password field (login, register, change password, reset, admin re-authentication, admin account creation) is rendered as `<input type="password">`, so the browser shows dots. All responses carry `Cache-Control: no-store`. |
| 2.1.8 Enforce account disabling after an established number of invalid login attempts | Unlimited password guessing (online brute force). | An attacker scripts thousands of login attempts against one account until the password is found. | `users.failed_count` is incremented on every failed login or failed security-answer attempt. On the 5th consecutive failure `locked_until` is set to the current time + 15 minutes and the counter is reset. While `locked_until` is in the future every login or reset attempt is refused, even with the correct password, with the same generic message. The lock expires on its own after 15 minutes, which limits an attacker to 5 guesses per 15 minutes per account while preventing a permanent denial of service against the legitimate user. A successful login resets the counter. Lockouts are logged as `AUTH FAILURE` ("lockout triggered" / "account locked"). |
| 2.1.9 Password reset questions should support sufficiently random answers | Reset questions with a small set of common answers (e.g. favorite book, favorite color). | An attacker resets a victim's password by guessing "The Bible" or "blue". | Users choose from a fixed list (`SECURITY_QUESTIONS`) of questions whose answers are personal and high-entropy: first-grade teacher's name, license plate of the family's first car, full name of childhood best friend, street name and number of first home, model of first mobile phone. Free-text questions are not allowed. Answers must be 6–100 characters, are stored as salted scrypt hashes, and wrong answers count toward the 5-attempt lockout. |
| 2.1.10 Prevent password re-use | Users rotating back to an old (possibly compromised) password. | A password exposed in an earlier breach is set again and the old leaked credential works once more. | Every password a user has ever had is kept, as a salted scrypt hash, in the `password_history` table. On password change and on password reset the candidate is verified against every history row for that user; a match is rejected with "Password was used before." Because the whole history is checked (not just the last N), cycling through passwords cannot bring an old one back. |
| 2.1.11 Passwords should be at least one day old before they can be changed | Rapid successive password changes used to flush a history list and return to the original password. | A user changes their password several times in a minute to get around the re-use rule. | `users.pw_changed_at` records the time of the last change. `POST /password` rejects the request with "Password was changed less than one day ago." if fewer than 24 hours have passed. The seeded demo accounts are created with `pw_changed_at` two days in the past so the change can be demonstrated. |
| 2.1.12 The last use (successful or unsuccessful) of a user account should be reported to the user at their next successful login | Users have no way of noticing that someone else has used or attacked their account. | An attacker's failed guesses or successful login go unnoticed, so the victim never changes the password or reports it. | Every login attempt against an existing account updates `last_use_at`, `last_use_ok` and `last_use_ip`. On a successful login the previous values are read first and stored with the new session; the home page shows them, e.g. "Last account use: 2026-11-14 08:00:00 UTC — unsuccessful login attempt from 127.0.0.1". |
| 2.1.13 Re-authenticate users prior to performing critical operations such as password change | Critical actions performed on an unattended or hijacked session. | Someone using an unlocked computer changes the victim's password, or creates a new administrator account. | Password change requires the current password. The three administrator operations — create account, change role, delete account — require the acting administrator's password in the `admin_password` field. The password is verified with scrypt before anything is changed; a wrong password returns HTTP 400, changes nothing, and is logged as `AUTH FAILURE` "re-auth failed". |

### 2.2 Authorization / Access Control

| Security Requirement / Issue | Vulnerability | Impact | Security Control |
|---|---|---|---|
| 2.2.1 Use a single site-wide component to check access authorization | Authorization checks copied into individual pages, where one is eventually forgotten. | A new or edited page ships without its role check and customers can reach a manager or administrator function. | Authorization is done in exactly one place: `authorize()`, called by `dispatch()` for every request before any handler runs. The policy is data, not code: each row of the `ROUTES` table is `(method, path pattern, handler, allowed roles)`. Handlers contain no role checks of their own, so a route cannot exist without a declared role set. The same dispatcher also enforces the CSRF token (per-session random token compared with `hmac.compare_digest`) and `Origin` check on every POST. |
| 2.2.2 Access controls should fail securely | Access checks that default to "allow" when something unexpected happens. | An unknown role value, an expired session or an exception during the check lets the request through. | Deny by default. `authorize()` returns "allowed" only when the session's role is a member of the route's allowed set; a missing session, an unknown role, an unmatched route (404) or any exception results in denial (302 to `/login` or a 403 page). The role is read from the database on every request, so a deleted or demoted user loses access immediately; deleting a user cascades to their sessions. |
| 2.2.3 Enforce application logic flows to comply with business rules | Users skipping steps or acting on objects they do not own (IDOR), or performing actions out of sequence. | A customer cancels another customer's order by changing the id in the URL, orders more than the stock, or edits an order that has already been fulfilled. | Rules are enforced on the server on every request: (1) customers can only view, edit or cancel orders whose `user_id` equals the session user — otherwise 403 and an `ACCESS FAILURE` "not owner" log entry; (2) only `pending` orders can be edited, cancelled or have their status changed; (3) order quantity cannot exceed available stock, and stock is adjusted in the same transaction; (4) a product with pending orders cannot be deleted; (5) public registration always creates a `customer`; (6) administrators can only create/assign/delete `admin` and `manager` accounts, never customers, and cannot modify or delete their own account; (7) password change requires a password at least one day old. |

### 2.3 Data Validation

| Security Requirement / Issue | Vulnerability | Impact | Security Control |
|---|---|---|---|
| 2.3.1 All validation failures should result in input rejection. Sanitizing should not be used. | Malformed or malicious input accepted, or "cleaned" into something unintended. | Injection (SQL, HTML/script) or corrupted records; sanitizers that strip characters can be bypassed or silently change what the user meant. | All input goes through allow-list validators (`v_str`, `v_int`, `v_price`, `v_choice`, `v_password`) that use `re.fullmatch`. On any failure they raise `ValidationError`; `dispatch()` rejects the whole request with an HTTP 400 page and nothing is written to the database. Input is never trimmed, truncated, escaped or otherwise altered before validation or storage. Duplicate fields, more than 50 fields, and bodies over 10,000 bytes (HTTP 413) are rejected. As defense in depth, every SQL statement is parameterized and every value written into HTML is encoded with `html.escape` (output encoding, not input sanitizing). |
| 2.3.2 Validate data range | Numeric values outside what the business allows. | An order for 0 or 1,000,000 items, a negative stock level, or a negative price that turns an order total into a credit. | Numeric inputs must be all digits (`\d{1,9}`, so no signs or exponents) and are then range-checked: order quantity 1–100; product stock 0–100,000; product price 0.01–1,000,000.00 (`\d{1,7}(\.\d{1,2})?`, stored as integer cents); log page number 1–100,000. Choice fields (role, order status, security question, log category/outcome) must be one of the listed values. Dates in log filters must match `YYYY-MM-DD`. |
| 2.3.3 Validate data length | Over-long input. | Storage exhaustion, broken page layout, or denial of service through very large fields (including CPU exhaustion in password hashing). | Every text field has a minimum and maximum length checked by `v_str`: username 3–30 (`[A-Za-z0-9_]` only); password 12–128; security answer 6–100; product name 1–100; product description 0–500. The whole request body is limited to 10,000 bytes. |

### 2.4 Error Handling and Logging

| Security Requirement / Issue | Vulnerability | Impact | Security Control |
|---|---|---|---|
| 2.4.1 Use error handlers that do not display debugging or stack trace information | Stack traces and debug output sent to the browser. | An attacker learns file paths, SQL statements, library versions and code structure and uses them to craft further attacks. | `dispatch()` wraps every handler in a catch-all `except`. The traceback is written only to the server-side file `data/error.log` (not reachable through any route), an `ERROR FAILURE` row containing only the exception class name goes to the audit log, and the client receives the generic 500 page. The `Server` header is reduced to `SecureShop` (no Python or library version) and the default `http.server` error page (used by the library for malformed requests and unsupported methods) is replaced with a one-line generic message. |
| 2.4.2 Implement generic error messages and use custom error pages | Default server error pages and detailed error messages. | Default pages reveal the technology in use; detailed messages reveal why a request failed. | The application has its own pages for 400, 403, 404, 405, 413 and 500, all rendered through the same `page()` layout with short generic text (e.g. "Something went wrong. Please try again later."). Authentication-related failures use fixed generic messages (see 2.1.4). |
| 2.4.3 Logging controls should support both success and failure of specified security events | Logging only failures (or only successes), leaving an incomplete audit trail. | After an incident it is impossible to tell which attempts succeeded, e.g. whether a brute-force run ended in a successful login. | One function, `log()`, writes every event to the `audit_log` table with: UTC timestamp, username, client IP, category (`AUTH`, `ACCESS`, `VALIDATION`, `DATA`, `ADMIN`, `ERROR`), event, outcome (`SUCCESS` or `FAILURE`) and detail. Successes logged: login, logout, registration, password change/reset, product and order changes, user creation/role change/deletion. Failures logged: see 2.4.5–2.4.7. Passwords, answers and session tokens are never logged. |
| 2.4.4 Restrict access to logs to only website administrators | Logs readable (or editable) by ordinary users. | Users read other people's activity, or an attacker erases their tracks. | `GET /admin/logs` is the only route that reads `audit_log`, and its allowed-role set is `{admin}`; managers and customers receive 403 (which is itself logged). Access is read-only: there is no route that updates or deletes log rows. The administrator can filter by category, outcome, username and date range, and page through the results. The log lives in the database and `data/error.log` on disk; neither is served as a file. |
| 2.4.5 Log all input validation failures | Validation failures discarded silently. | Probing for injection or tampering with form fields goes undetected. | `ValidationError` is caught in one place (`dispatch()`), which logs a `VALIDATION FAILURE` row with the validation message (which field or rule failed) and the request path before returning the 400 page. Because every validator raises the same exception, no validation failure can bypass logging. Rejected passwords and answers are never included in the detail. |
| 2.4.6 Log all authentication attempts, especially failures | No record of logins. | Brute-force and credential-stuffing attacks, or logins from unusual addresses, cannot be detected or investigated. | Every login attempt is logged under category `AUTH` with the username supplied, the client IP and the outcome. Failure details distinguish "unknown user", "wrong password", "account locked" and "lockout triggered" (in the log only). Registration, logout, password change, password reset and re-authentication failures are also logged. |
| 2.4.7 Log all access control failures | Unauthorized access attempts not recorded. | A user repeatedly probing administrator URLs or other users' order ids is never noticed. | Every denial produces an `ACCESS FAILURE` row with the user, role, IP and path: unauthenticated request to a protected route, role not allowed for the route (403), order not owned by the user ("not owner"), and missing/incorrect CSRF token or `Origin` ("csrf"). |

## 3. Additional Hardening

These are not checklist items but support the controls above.

| Security Requirement / Issue | Vulnerability | Impact | Security Control |
|---|---|---|---|
| Session management | Predictable, long-lived or reusable session identifiers; session fixation. | An attacker guesses, steals or pre-sets a session identifier and acts as the victim without knowing the password. | Session token from `secrets.token_urlsafe(32)`; only its SHA-256 is stored. Cookie flags `HttpOnly; SameSite=Strict; Path=/`. New token at every login (no session fixation), 30-minute idle timeout, the session is destroyed on logout; a password change destroys the user's other sessions; a password reset or account deletion destroys all of them. |
| Cross-site request forgery (CSRF) | State-changing requests accepted from other websites using the victim's cookie. | A malicious page silently submits a form that cancels the victim's orders or, for an administrator, deletes an account. | A random token (`secrets.token_urlsafe(32)`) is generated per session, embedded as a hidden field in every form, and compared with `hmac.compare_digest` in `dispatch()` on every authenticated POST. If an `Origin` header is present it must equal the site's own origin. The cookie is `SameSite=Strict`. Failures return 403 and are logged. |
| Browser-side protections (HTTP headers) | Clickjacking, MIME sniffing, injected script execution, cached sensitive pages. | The site is framed by a hostile page to trick clicks, or a private page is read from the browser cache on a shared computer. | Every response carries `Content-Security-Policy: default-src 'self'` (the app has no inline script or style), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` (no referrer or origin is disclosed to other sites), `Cache-Control: no-store`. |
| SQL injection | User input concatenated into SQL statements. | An attacker logs in without a password, reads the users table or deletes data by typing SQL fragments into a form. | Every statement uses `sqlite3` parameter binding (`?` placeholders); no SQL text is ever built from request data. Input is additionally allow-list validated first (2.3.1). |
| Cross-site scripting (XSS) | User-supplied text written into pages as HTML. | A product name containing a script runs in other users' browsers and performs actions with their session. | Every dynamic value is encoded with `html.escape(value, quote=True)` through one helper, `e()`, at the point of output. The CSP above blocks inline and third-party script as a second layer; the application ships no JavaScript. |
| Path traversal / static file exposure | A file-serving route that maps URL paths to disk paths. | An attacker requests `/static/../data/shop.db` and downloads the database or source code. | Exactly one static file, `/static/style.css`, is served, from a fixed path that never includes request data. The database and error log are outside any served location. |
| Server version disclosure | Software and version shown in the `Server` header. | An attacker looks up known vulnerabilities for the exact Python version. | `server_version` is set to `SecureShop` and `sys_version` to an empty string. |
| Oversized requests | Unbounded request bodies or field counts. | Memory or CPU exhaustion (denial of service). | Bodies over 10,000 bytes are refused with 413 before being read; at most 50 form fields are parsed. |

## 4. Known Limitations

- The demo server speaks plain HTTP on `127.0.0.1`; the session cookie therefore has no `Secure` flag. A real deployment must sit behind TLS and add the flag.
- Accounts created by an administrator have no security question and therefore cannot use self-service password reset; an administrator must recreate the account.
- An account created by an administrator keeps the administrator-chosen password for at least one day because of the minimum password age rule (2.1.11).
- The seeded demo passwords are published in this document and the README and must be changed outside a demo environment.
